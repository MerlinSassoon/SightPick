# 架构说明：从“招聘采集”到“视觉 RPA 工程样品”

> 这份文档回答三个问题：
> 1. SightPick 的核心抽象是什么？
> 2. 哪些部分是招聘领域特定的，哪些可以迁移到别的领域？
> 3. 如果要扩到第二个领域，应该从哪里下手，不应该从哪里下手？

---

## 1. 设计目标

SightPick 的目标不是“写一个 BOSS直聘爬虫”，而是验证一条通用的视觉 RPA 路线：

```text
用户框选区域 → 配置区域行为 → 程序看屏幕、点击、滚动
             → OCR 认字 → 视觉大模型做语义确认/去噪
             → 结构化记录逐条落盘
```

它适合的场景有一个共同前提：**目标系统没有可用的 API/DOM，或者通过 DOM 接入的成本/风险高于看屏幕。**

因此，架构上刻意把“招聘”收敛到配置层，把“看屏幕”做成可替换的驱动层：

- 屏幕驱动、OCR、LLM 都是可替换的；
- 两种模式是通用原语，不依赖招聘语义；
- 具体站点的坐标、停止标志、锚点、输出映射都在计划 JSON 里；
- 真实运行与 mock 运行共享同一套编排。

---

## 2. 分层

| 层 | 主要组件 | 职责 | 领域相关性 |
| --- | --- | --- | --- |
| 交互层 | `app/streamlit_app.py`、`plan_builder.py` | 截图、框选、配置、滚动测试、启动/查看运行 | 低；文案目前偏招聘 |
| 计划层 | `models/config.py`、`plan_io.py`、`profile_io.py` | 区域字典、区域配置、运行参数、校验、保存/加载 | 低；字段名有历史包袱 |
| 执行层 | `orchestrator.py`、`modes/*` | 按计划实例化模式、遍历、点击、滚动、停止、组装 | 低 |
| 感知层 | `capture/*`、`ocr/*`、`llm/*` | 截图/点击/滚动、OCR、视觉确认、去噪 | 低 |
| 存储层 | `storage/writers.py`、`storage/reader.py` | JSONL 增量写、JSON 汇总、运行报告、结果读取 | 低；输出字段可映射 |
| 前端展示 | Streamlit 结果页 | 只读预览、日志、报告 | 低；目前是附加项 |

**关键设计**：执行层不知道“招聘”这件事。它只知道“区域、模式、滚动、停止条件、调用关系、输出映射”。招聘语义只存在于配置和少量文案里。

## 3. 数据流

```text
GUI 页面
  │
  ├─ ScreenDriver.capture(region) ──► Frame(image, region, label)
  │
  ├─ OcrEngine.recognize(frame) ───► OcrLine[](text, score, box)
  │
  ├─ BaseRegionMode
  │    ├─ 列表导航（sms）：点击列表项 → 调用抄录区域 → 组装
  │    └─ 区域抄录（transcribe）：截图/滚动/停止/去重/去噪
  │
  ├─ LLMClient（按需）
  │    ├─ confirm_anchor：首轮锚点确认/纠错
  │    ├─ confirm_click：点击是否命中新条目（可选）
  │    └─ denoise：文本清理/结构化（可异步）
  │
  └─ Orchestrator
       ├─ 批次完成或中断暂停时，把已完成记录 append + fsync 到 jobs.jsonl
       ├─ 运行结束/用户结束时写 jobs.json / capture_report.json
       └─ 可选复制到 output.dir
```

### 中断控制通道（暂停 / 继续 / 结束）

条目捕获阶段出现可预期的 `RecruitingError` 时：

- 子进程先等待异步去噪，再保存已完成 items；
- 写 `interrupt_status.json`（`state=paused`、原因、已保存条数）；
- 恢复前端窗口，轮询 `interrupt_decision.json`；
- 前端“继续采集”写 `resume`，后端重试当前条目；
- 前端“结束采集”写 `stop`，后端保留数据并正常退出；
- 超时（默认 30 分钟）按结束处理。

这是文件级 IPC，不引入额外服务；`runtime/` 已被 gitignore，控制文件不会上传。

### 为什么先裁切、再 OCR

`pyautogui.screenshot(region=...)` 直接截取目标区域，OCR 只处理这一小块。
好处是：定位误差不会扩散到全屏，视觉大模型拿到的也是同一块图；代价是：区域坐标必须与屏幕/DPI 一致。

### 为什么 OCR + LLM 两级

- OCR 负责“看见字”，快、便宜、但会错字/漏字/把界面元素当正文；
- LLM 负责“判断语义”，例如锚点是否存在、点击是否命中、哪些行是噪声；
- 规则层（停止标志、去重、噪声黑名单）负责兜底，避免所有判断都依赖 LLM。

这不是“LLM 万能”，而是“OCR 便宜、LLM 贵，把 LLM 用在需要语义的地方”。

## 4. 两种模式：通用语义

### 4.1 列表导航模式（代码名 `sms`）

历史名叫“短信模式”，实际语义是 **list navigation**：

- 在一个列表区域里找到可点击的条目；
- 点击条目，等待页面刷新；
- 调用一个或多个抄录区域；
- 可选：滚动列表，继续下一条；
- 用“键区域 + 值区域”组装字典，或用集合模式组装列表。

适合：岗位列表、订单列表、客户列表、文件列表、邮件列表。

### 4.2 区域抄录模式（代码名 `transcribe`）

语义是 **region transcription**：

- 对一个区域截图 + OCR；
- 可选滚动，直到命中停止标志或达到最大轮次；
- 去重、去噪、按期望格式（str/list/tuple）归一；
- 返回文本或文本列表。

适合：职位描述、发票字段、日志面板、合同条款、报表正文、旧版软件的表单。

### 4.3 组合关系

```text
列表导航 A
  ├─ 抄录 B（键区域，expected_format=str）
  └─ 抄录 C（值区域，expected_format=list）
        ↓
   {B: [C 的文本行...]}
```

领域差异主要落在：

- 区域坐标；
- 滚动起点/距离；
- 停止标志；
- 锚点；
- 输出字段映射；
- 少量噪声规则。

执行引擎、驱动、OCR、LLM、存储都可以复用。

## 5. 配置模型

一份计划由四块组成：

| 块 | 内容 | 例子 |
| --- | --- | --- |
| `screen` | 设计分辨率、截图尺寸 | 1920×1080 |
| `regions` | 区域名 → `[xmin, ymin, xmax, ymax]` | A 列表、B 标题、C 描述 |
| `region_configs` | 每个区域的模式与行为 | 列表/抄录、滚动、停止、锚点、格式 |
| `output` / `run` | 输出映射、引擎、LLM、并发、超时 | title_region=C、engine=real |

**优点**：页面改版通常只需要改坐标/停止标志，不需要改执行代码。
**代价**：坐标、DPI、滚动距离、停止标志仍然需要人工校准；这不是“零配置”。

## 6. 扩展点

| 想扩展什么 | 从哪里下手 | 是否需要改执行层 |
| --- | --- | --- |
| 新站点/新桌面软件 | 新建计划 JSON + 配置档案；定义区域、模式、停止条件、输出映射 | 通常不需要 |
| 新 OCR 引擎 | 实现 `OcrEngine` 协议，在 `engines.py` 里构建 | 不需要 |
| 新视觉/文本 LLM | 实现 `LLMClient` 协议，在 `build_llm()` 里构建 | 不需要 |
| 新输出格式 | 扩展 `JobRecord`/writer，或在 `output.extra_fields` 做映射 | 小改 |
| 新交互模式 | 继承 `BaseRegionMode`，增加配置模型与校验，在 orchestrator 里实例化 | 需要 |
| 新 UI | 保留 CLI/编排，替换 Streamlit 层 | 不需要改核心 |
| 新领域文案 | 改 UI 文案/文档；代码里的 `sms` 命名可后续重构 | 仅文案/命名 |

> 当前代码没有插件注册机制；扩展主要靠“实现协议 + 在组合根 wiring”。这是工程样品级别的可扩展性，不是平台级插件系统。

## 7. 哪些是领域特定的

| 部分 | 领域特定？ | 说明 |
| --- | --- | --- |
| BOSS 的 A/B/C 坐标 | 是 | 只在 `configs/boss_1080p_example.json` / profile 中 |
| `企业服务`、`去App`、`工作地址` 等停止标志 | 是 | 配置项，不写死在执行层 |
| 招聘标题/描述/噪声规则 | 部分是 | 规则层有招聘词表；其他领域需要补充 |
| 两种模式 | 否 | 列表导航/区域抄录是通用原语 |
| 驱动/OCR/LLM/存储 | 否 | 可替换 |
| Streamlit 文案 | 部分是 | 目前写的是“招聘/岗位”；换领域需要改文案 |
| 输出字段 `job_title`/`job_desc` | 部分是 | 当前是招聘语义；多领域可加通用字段或做映射 |

**结论**：核心执行层已经是领域无关的；领域差异主要在配置、文案、输出 schema 和少量规则。
这也意味着：如果要把它做成真正的多领域工程样品，下一步不是“再加一个模式”，而是把**命名、schema、文案、输出适配**这四件事工程化。

---

## 8. 如果要扩到第二个领域，建议的顺序

1. **先选一个“没有 API/DOM、但你有权操作”的系统**：企业内部 ERP、旧版 Windows 客户端、行业软件；
2. **用现有两种模式做最小配置**：一个列表 + 一个抄录区域；
3. **只改配置，不改代码**：验证“领域差异是否能被配置吸收”；
4. **记录失败模式**：坐标、滚动、停止条件、OCR 噪声、权限；
5. **再决定是否改代码**：如果配置能吸收 80% 差异，说明架构成立；如果每个领域都要改执行层，说明抽象不够；
6. **最后再谈 UI/产品化**：不要先做“通用平台”，先用第二个领域证明复用。

---

## 9. 非目标

- 不做“绕过平台风控/验证码”的能力；
- 不做高并发、无头、多用户的采集平台；
- 不承诺“页面改版零维护”；
- 不把当前 Streamlit UI 当成完整产品；
- 不在没有授权/合规评估的情况下商业化。
