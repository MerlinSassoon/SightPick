# 路线图：从视觉 RPA 工程样品到多领域复用

> 当前定位：**视觉 RPA 工程样品**，以 BOSS直聘为第一个案例。
> 目标不是马上做“平台”，而是证明两件事：
> 1. 视觉 RPA 在真实 GUI 上能跑；
> 2. 这套抽象能迁移到第二个领域，而不是只能服务招聘。

---

| 能力 | 状态 |
| --- | --- |

| PaddleOCR 真实识别 | ✅ |

## 1. 阶段一：把“能跑”变成“能用”（2–4 周）

**目标**：同一页面、同一配置下，稳定产出 20 条**可直接分析**的记录。

| 工作 | 验收 |
| --- | --- |
| 20 条 ground truth | 人工标注标题、完整描述、噪声行、PII |
| 标题治理 | 不混薪资/公司/标签；保留方向后缀；准确率 ≥95% |
| 描述治理 | 清掉标题/地址/标签/PII；完整率 ≥95%；噪声 ≤2% |
| 锚点治理 | 首轮失败重试/等待/跳过；20 条锚点失败率 ≤5% |
| 停止条件 | 不再只依赖 `去App`；增加内容长度/滚动上限保护 |
| 隐私 | 默认不保存截图；LLM 前 redaction；输出 PII 行 0 |
| 成本 | 记录单条耗时、LLM 调用、token/费用 |

**产出**：`docs/BENCHMARK.md`（或更新 `EVIDENCE.md`）里一张“当前 vs 目标”的表。

---

## 2. 阶段二：把“招聘案例”变成“通用原语”（1–2 个月）

**目标**：用第二个领域证明复用，而不是继续加招聘功能。

### 2.1 命名与 schema

- `sms` → `list`，`transcribe` → `region`（代码重构，另开 PR）；
- 输出字段从 `job_title`/`job_desc` 抽象为 `record_key`/`record_body`，或增加领域适配层；
- 计划 schema 增加 `domain`/`profile` 元信息；
- UI 文案从“岗位”抽象为“条目/记录”。

### 2.2 第二个领域

优先选择：

- 企业内部 ERP/CRM 的列表 + 详情；
- 旧版 Windows 客户端的数据导出；
- 行业软件中的报表/表单；
- **必须是你有权操作、条款允许的系统**。

验收：

- 只改配置/文案，不改执行层，能跑通 3–5 条；
- 记录哪些差异被配置吸收，哪些必须改代码；
- 如果每个领域都要改执行层，说明抽象不够，先别做平台。

### 2.3 输出适配

- 通用 JSONL schema；
- 可选的 CSV/JSON 导出；
- 字段映射配置；
- 数据校验（必填、类型、去重、PII）。

---

## 3. 阶段三：选择产品方向（3 个月后）

### 方向 A：授权场景的视觉 RPA（更推荐）

- 客户：有老旧系统、没有 API 的企业；
- 价值：不改造原系统，做数据抽取/录入；
- 要求：审计、权限、人工复核、稳定性、合规；
- 商业模式：项目制/授权制，而不是“卖爬虫”。

### 方向 B：求职分析助手

- 用户：个人求职者；
- 数据：用户导出/授权数据，避免直接抓 BOSS；
- 价值：岗位对比、技能 gap、薪资分布、简历匹配；
- 要求：结构化字段、清洗、分析模型、隐私设计。

**不要同时做 A 和 B。** 先选一个，另一个作为远期。

---

## 4. 非目标（明确不做）

- 不绕过登录/验证码/访问控制；
- 不做高并发、无头、多用户的采集平台；
- 不承诺“页面改版零维护”；
- 不先做完整可视化平台；
- 不在没有授权/合规评估的情况下商业化；
- 不把“能跑 5 条”包装成“已可规模化”。

---

## 5. 里程碑

| 里程碑 | 标志 |
| --- | --- |
| M1 可信原型 | 20 条 ground truth；标题/描述达标；PII 0 |
| M2 多领域验证 | 第二个领域只改配置即可跑 3–5 条 |
| M3 工程样品 | 一键 demo、脱敏证据、benchmark、release checklist |
| M4 产品验证 | 一个真实用户每周使用；一个可付费场景 |
| M5 商业化 | 授权/合规/成本/服务能力齐全 |
