## 2. 问题复盘与根因分析

本节将“日志中观察到的数据现象”与“现场人工排查的实际成因”逐一对应，给出根因判定与影响面。

### 2.1 停止条件异常与人工介入（P0）

**现象（数据侧）**

- `stop_reason = user_stopped`、`stop_marker = null`，同时 `max_jobs = 1000` 远未达到；
- `warnings` 中 3 条为锚点失败暂停，`partial_saves` 三次保存 `new = 55 / 324 / 2`，累计 381 条；
- 3 次暂停均由同一错误分支触发：`区域 C 首轮未识别到锚点“职位描述”，视觉大模型确认页面中不存在该内容`。

**根因（现场 + 代码行为合并判定）**

| 暂停序号 | 直接成因 | 根因层次 | 判定 |
| --- | --- | --- | --- |
| 第 1 次（55 条） | 滚动微小误差累积 → 岗位偏离悬停位置 → 点击为空/误点 → 右侧未更新，停留在上一岗位底部 | **坐标漂移（累积误差）** | 交互层根因，非 OCR 问题 |
| 第 2 次（379 条） | 网络波动 → 点击后右侧白屏刷新 | **页面异步加载未就绪** | 时序根因，非 OCR 问题 |
| 第 3 次（381 条） | 同类点击后内容未正常加载现象 | 同上两类之一 | 同类问题复现 |

**关键结论**

1. **“无新增文本兜底”是成功的设计**：3 次 C 区“连续 2 轮无新增文本，防止死循环提前结束”均正确触发（10:45:47 / 11:05:18 / 11:47:51），说明滚动循环具备自我保护能力。
2. **“锚点失败兜底”不够优雅**：当前以“暂停整批 + 恢复窗口 + 等待人工”为唯一降级路径，把**单条异常**放大为**整批中断**。三次暂停合计造成约 248 秒的人工等待，并且第 3 次直接导致批次以人工结束收尾。
3. **错误归因不准确**：LLM 被问“页面中是否存在该内容”，而真实原因是“右侧内容尚未刷新/点击未生效”，这是**把交互失败误判为页面内容缺失**，会误导操作者去“检查区域框选”。

**影响**：可用性受损（需值守）、吞吐降低（约 4 条/分钟）、批次终止不可预期。

### 2.2 跨条目去重失效（P0）

**现象（数据侧）**

| 指标 | 数值 |
| --- | --- |
| 记录总数 / 去重标题数 | 381 / 201 |
| “标题 + 描述”完全重复组 | 86 组，**冗余 112 条（29.4%）** |
| 描述签名完全相同组 | 61 组（单组最多重复 4 次） |
| 出现最多的标题 | 运维工程师 ×7、RPA开发工程师（双休）×6，另有 5 个标题各 ×4 |

**根因（现场反馈）**

BOSS直聘等平台采用**“无限加载 + 已读置灰”**机制：列表长期向下滚动刷新后，**已被点击过的置灰岗位会再次进入采集视野**；而视觉 RPA 只能"看到"列表项，无法识别"置灰"这一状态，于是重复点击、重复落盘。

> 这修正了原先"滚动重叠导致重复"的推断：**重叠只是表象，真实机制是平台侧的已读状态回填 + 自动化无法感知置灰**。

**为什么 `jobs.json` 看起来“0 重复”**：`jobs.json` 以标题为键，201 个键天然掩盖了 180 条冗余；重复问题**只有在 `jobs.jsonl` 行级别才可见**。README 中“35 条真实记录描述重复行 0 重复”的结论**在本次大批量运行中不成立**。

**影响**：后续任何按行统计（薪资分布、岗位数量、词频）都会被系统性地放大近 30%。

### 2.3 数据去噪与标题质量（P1）

**描述噪声现状**

| 噪声类型 | 命中 | 处理意见（人工判定） |
| --- | ---: | --- |
| 首行平台标签 `标签：…`（如"五险一金"类标签串） | 305 / 381（80.1%） | **可接受，保留** |
| `工作地址` 版块 | 192 / 381（50.4%） | **必须去除** |
| 地图碎片（如"清龙路""天富楼""C2栋""694""出口"等 POI 行） | ≥1 条（末尾 14 行全为地图文本） | **必须去除** |
| `点击查看地图` | 4 | 随地图碎片一并去除 |
| `职位描述` 标题行 | 67 | 随去噪规则一并规范 |
| OCR 错字/跳号（`ExceI`、编号缺号、"新资组成"等） | 少量 | 观察项，暂不专项处理 |

**判定**：去噪链路**工作正常但不达标**——768 次 LLM 调用、0 等待，证明吞吐健康；但输出仍保留地址与地图 UI 区段，说明当前规则停留在"去空行/去重行"级别，缺少"**去除页面 UI 版块**"的显式约束。这也是"描述行数看起来很多但不都是职位描述"的根本原因。

**标题质量**

| 缺陷类型 | 命中 | 处理意见（人工判定） |
| --- | ---: | --- |
| 薪资混入（如 `算法工程师 12-24K`、`软件开发岗位 19-20K`、`…150元/天`） | 23 个唯一标题 | **次要问题**，后续加正则过滤 |
| 截断（以 `...` 结尾） | 5 个 | 次要 |
| **缺少时间戳** | **全部 381 条** | **最主要问题**，下阶段强制附加采集时间戳 |

**判定**：标题缺陷的主要矛盾已从"薪资混入"转移为"**缺乏时间维度标识**"——这既影响数据可追溯性，也是下一步用业务手段解决重复入库的前提（见 §4.3）。

### 2.4 字段映射与可观测性（P2）

- `company`、`salary` 在 381 条中**全为 `null`**：当前计划只映射 B/C 两区，属计划配置范围内，不是采集失败；但意味着薪资/公司维度完全缺失。**该能力被明确划为拓展模块**，不在核心流程中实现（见 §5.1）。
- 报告字段不足以自助排障：`stop_marker = null` 无法区分"人工结束"与"超时结束"；缺少"每类停止原因计数""锚点失败样本定位"等诊断字段。
- `console.log` 存在 UTF-8 与本地编码混入行，不利于自动化解析。

## 3. 当前架构的优越性与不足

### 3.1 优越性（本批次已实证）

| 能力 | 本批次证据 | 价值 |
| --- | --- | --- |
| **异步去噪 worker（有界队列 + 单一屏障）** | `llm_calls_async = 765`、`llm_wait_ms = 0` | 主流程从不等待 LLM，是本次 94 分钟 / 381 条吞吐的基石 |
| **逐条增量落盘（flush + fsync）** | 3 次暂停、1 次人工结束，数据零丢失 | 中断保护真实生效 |
| **中断/暂停/继续/结束状态机** | 2 次"继续" + 1 次"结束"全部正确闭环 | 比"锚点失败即整批终止"明显更可用 |
| **循环自保护** | 3 次"连续 2 轮无新增文本"正确提前结束 | 避免死循环 |
| **LLM 调用重试与降级** | 2 次 `RemoteDisconnected` 均重试成功 | 外部依赖不稳定时不崩 |
| **配置驱动（区域/停止/锚点/映射）** | 全程未改代码即可运行 | 领域差异收敛到配置层 |

### 3.2 不足（本批次暴露）

| 不足 | 证据 | 后果 |
| --- | --- | --- |
| **人工介入机制"有用但太频繁"** | 94 分钟内 3 次暂停，均需人工判断 | 批次实际不可无人值守 |
| **阻断式降级** | 单条异常即暂停整批 | 一条异常 = 一次值守 |
| **错误归因错位** | 交互失败被表述为"页面中不存在该内容" | 排查方向被误导 |
| **缺乏跨条目指纹去重** | 冗余 112 条（29.4%） | 统计口径失真 |
| **缺乏滚动漂移/页面刷新治理** | 首停因漂移、次停因白屏 | 交互稳定性依赖运气 |
| **停止条件与 UI 元素耦合** | C 区主要靠 `去App` 命中（378 条） | 提前截断风险 |
| **无时间维度** | 381 条标题无时间戳 | 无法区分同一岗位的多日样本 |
| **可观测性不足** | `stop_marker=null`、无失败样本定位 | 事后复盘依赖人工日志检索 |

## 4. 下阶段优化 Action 清单

> 原则：**优先用配置、流程与提示词解决，暂不扩张核心代码的领域逻辑**。所有条目标注验收方式。

| # | 优先级 | 事项 | 具体做法 | 验收标准 |
| --- | --- | --- | --- | --- |
| A1 | **P0** | **固定批次强制刷新** | 每采集固定 N 条（初值 **30 条**）后强制整页刷新一次，同时解决两件事：① 清除"已读置灰"回填导致的重复；② 重置滚动坐标漂移 | 连续 2 个批次重复率 ≤5%；漂移类暂停 = 0 |
| A2 | **P0** | **锚点失败柔性降级** | 由"暂停整批"改为"**自动跳过当前条 + 记账**"：写入 `skipped.jsonl`（含时间、坐标、失败类型），仅在连续失败达到阈值（如连续 3 条）时才暂停 | 单条失败不再中断批次；跳过可审计可回溯 |
| A3 | **P0** | **去重与刷新逻辑联调** | A1 生效后，对 `jobs.jsonl` 做行级指纹统计（标题 + 描述前 N 字），作为每批次固定指标写入报告 | 报告内出现"行级重复率"字段；冗余 ≤5% |
| A4 | **P1** | **时间戳防重（业务手段）** | 提取标题时**强制附加采集时间戳**；以"标题 + 时间戳"作为入库键，使重复岗位成为不同键值，**保证入库不覆盖** | 任意两次点击同一岗位不再互相覆盖；`jobs.json` 键数 = 行记录数 |
| A5 | **P1** | **去噪提示词（System Prompt）优化** | 通用过滤规则：去除 `工作地址` 版块及其后续地址内容、去除地图相关碎片（`点击查看地图`、路段名、楼栋名、门牌号等 POI 行）；**保留**平台标签行 | 抽样 20 条：地址命中 0、地图碎片 0；标签行保留率 ≥95% |
| A6 | **P2** | **标题正则清理** | 对"混入薪资"做正则剥离（`\d+-\d+K`、`\d+K`、`…元/天` 等），并入 `salary` 暂存字段 | 薪资混入标题 ≤1 条 / 20 条样本 |
| A7 | **P2** | **诊断字段补齐** | 报告增加：停止原因分类计数、跳过计数、锚点失败样本定位、行级重复率 | 复盘时无需检索 `run.log` |
| A8 | **P2** | **停止条件脱耦** | 在 `去App` 之外增加内容语义停止标志（如出现"工作地址"版块作为描述终结） | C 区提前截断率下降，且可通过人工抽检 |

## 5. 远期拓展边界

明确列出**当前不做**的事项与**留待未来**的方向，避免范围蔓延。

### 5.1 明确不做（本阶段）

| 事项 | 决策 | 理由 |
| --- | --- | --- |
| **公司名称/薪资等重字段校验** | 不做 | 需多区域映射 + 重逻辑校验，投入产出比不匹配当前阶段 |
| **自动脱敏（PII redaction）** | 不做 | 现有数据源中 PII 形态多变，规则化成本高；本阶段以"数据不外传"作为边界 |
| **手搓 RPA 工具化** | 不做 | 不在核心流程里堆砌领域逻辑 |
| **MySQL 入库 / 完整可视化看板** | 不做 | 与采集质量治理无直接关系 |

### 5.2 留待未来

| 方向 | 说明 | 前置条件 |
| --- | --- | --- |
| **模块化组装架构** | 未来形态是"模块化组装"：字段提取（薪资/公司）、去重、脱敏、入库各自作为可插拔模块挂载，而不是写死在核心流程里 | 核心流程稳定后（阶段一达标） |
| **多线程异步落盘** | 每个任务完成后**立刻带时间戳追加存档**，把去重/落盘的时序粒度从"批次"降到"任务" | A4 时间戳机制先落地 |
| **平台已读状态识别** | 从视觉特征（置灰颜色/透明度）识别已读项，从根上解决重复而非靠刷新规避 | 需专门的颜色/对比度采样研究 |
| **自动脱敏流水线** | 按 [PRIVACY.md](PRIVACY.md) 的分类做输出前过滤与 LLM 前 redaction | 字段结构稳定后 |
| **20 条 → 长稳批次** | 在 20 条验收通过后，推进多批连续长稳运行与成本（token/费用）统计 | 阶段一验收通过 |

---

## 6. 结论

1. **稳定性**：链路可用性达到新高度——94 分钟、381 条、零未捕获异常、零数据丢失，异步去噪与增量落盘经受住了真实中断考验。
2. **可用性**：人工介入机制**生效但过于频繁**（3 次/94 分钟），本质是"阻断式降级"与"错误归因错位"，应改为**自动跳过 + 记账**。
3. **正确性**：本批次**不能作为数据验收依据**——29.4% 行级冗余、50.4% 含地址、80.1% 含标签行。冗余根因是平台"无限加载 + 已读置灰"，需靠"固定批次刷新 + 时间戳键"双管齐下。
4. **下一步**：严格按 §4 的 A1 → A2 → A3（P0）推进，再执行 **20 条 ground truth 验收**，方可将本项目从"能跑"推进到"能用"。
